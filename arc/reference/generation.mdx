ARC generates through the API your client already speaks. Set `model` to an ARC ID; ARC chooses the model and reasoning effort, runs the turn, and returns the provider's response in the same format.

| Endpoint | Format | ARC support |
| --- | --- | --- |
| `POST https://api.rayline.ai/v1/messages` | Anthropic Messages | Yes |
| `POST https://api.rayline.ai/v1/chat/completions` | OpenAI Chat Completions | Yes |
| `POST https://api.rayline.ai/v1/responses` | OpenAI Responses | Not yet; see [availability](/arc/availability) |

Authenticate with your Rayline key in `x-api-key` or `Authorization: Bearer`. See [API keys](/platform/api-keys).

## Model IDs

| ID | What it is | Billed at |
| --- | --- | --- |
| `arc-swift` | ARC Swift, fixed V 0.1 | Swift's fixed rate card |
| `arc-sage` | ARC Sage, fixed V 4.5 | Sage's fixed rate card |
| `arc-1.0` | Configurable ARC | The served model's catalog price, no ARC fee |

`arc-1` (for `arc-1.0`) and the versioned tier IDs `arc-swift-1.0` and `arc-sage-1.0` are also accepted. Prefixed IDs such as `rayline/arc-swift`, and unknown `arc-*` IDs such as `arc-2.0`, return `404` (`not_found_error`, `Model not found`); a bare `arc` is not an ID.

## Routing extension

Add a `routing` object to the request body. Only `arc-1.0` takes your own value; the tiers accept only their own.

| Member | Type | Meaning |
| --- | --- | --- |
| `value_usd` | number, 0.1 to 5 | Your V, the US-dollar value of one successful result. On `arc-swift` or `arc-sage` it must equal the tier's V, or the request is refused with `tier_value_immutable`. |
| `temperature` | number, 0 or more | Routing temperature for hosted exploration. Capped by Rayline, and applied only when your organization's data setting allows ARC to learn from the request; otherwise it is not applied. |

`routing.prices` and `routing.exclusive` are accepted on [Decisions](/arc/reference/decisions#routing-controls) only; on generation they return `400` (`prices_not_supported`). The model's own `temperature` field is separate and passes to the provider as usual.

```bash
curl https://api.rayline.ai/v1/messages \
  -H "x-api-key: $RAYLINE_API_KEY" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"model":"arc-1.0","max_tokens":1024,
       "routing":{"value_usd":1.5},
       "messages":[{"role":"user","content":"Plan a zero-downtime schema migration."}]}'
```

Send the same `x-conversation-id` on every turn of a conversation so ARC decides each turn in context. Errors use the Anthropic error format; see [errors and limits](/arc/reference/errors).

## Conversation identity

An ARC request takes its conversation ID from the first of these that is present:

1. The `x-conversation-id` header.
2. The body field `prompt_cache_key`, on a request from Codex.

With neither, the turn is stateless.

Codex sets `prompt_cache_key` to its thread ID on every request, and each spawned subagent thread sends its own, so Codex gets multi-turn decisions and separate subagent conversations without any configuration. For any other client the field is a cache-grouping hint that may legitimately be shared across conversations, so it is not read; send `x-conversation-id`.

See [API compatibility](/arc/reference/compatibility) and [errors and limits](/arc/reference/errors).
