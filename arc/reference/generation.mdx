ARC generates through the API your client already speaks. Set `model` to an ARC ID; ARC chooses the model and reasoning effort, runs the turn, and returns the provider's response in the same format.

| Endpoint | Format | ARC support |
| --- | --- | --- |
| `POST https://api.rayline.ai/v1/messages` | Anthropic Messages | Yes |
| `POST https://api.rayline.ai/v1/chat/completions` | OpenAI Chat Completions | Yes |
| `POST <api-origin>/v1/responses` | OpenAI Responses | Where the model advertises `responses`; check [protocol support](/arc/availability#check-protocol-support) for your environment |

Authenticate with your Rayline key in `x-api-key` or `Authorization: Bearer`. See [API keys](/platform/api-keys).

## Model IDs

| ID | What it is | Billed at |
| --- | --- | --- |
| `arc-swift-1.0` | ARC Swift, fixed V 0.1 | Swift's fixed rate card |
| `arc-sage-1.0` | ARC Sage, fixed V 4.5 | Sage's fixed rate card |
| `arc-1.0` | ARC Dynamic | The served model's catalog price, no ARC fee |

`arc-1` is also accepted for `arc-1.0`. Prefixed IDs such as `rayline/arc-swift`, and unknown `arc-*` IDs such as `arc-2.0`, return `404` (`not_found_error`, `Model not found`); a bare `arc` is not an ID.

## Routing extension

Add a `routing` object to the request body. Only `arc-1.0` takes your own value; the tiers accept only their own.

| Member | Type | Meaning |
| --- | --- | --- |
| `value_usd` | number, 0.1 to 5 | Your V, the US-dollar value of one successful result. On `arc-swift-1.0` or `arc-sage-1.0` it must equal the tier's V, or the request is refused with `tier_value_immutable`. |
| `temperature` | number, 0 or more | Routing temperature for hosted exploration. Capped by Rayline, and applied only where the serving path supports it and your organization's data setting allows ARC to learn from the request. An `unsupported` status means the requested temperature was not applied. |

`routing.prices` and `routing.exclusive` are accepted on [Decisions](/arc/reference/decisions#routing-controls) only; on generation they return `400` (`prices_not_supported`). The model's own `temperature` field is separate and passes to the provider as usual.

```bash
curl https://api.rayline.ai/v1/messages \
  -H "x-api-key: $RAYLINE_API_KEY" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"model":"arc-1.0","max_tokens":1024,
       "routing":{"value_usd":1.5},
       "messages":[{"role":"user","content":"Plan a zero-downtime schema migration."}]}'
```

Send the same `x-conversation-id` on every turn of a conversation so ARC decides each turn in context. Errors use the Anthropic error format; see [errors and limits](/arc/reference/errors).

## Conversation identity

Send the same `x-conversation-id` on every turn you intend to group, and a new ID for a new conversation. This header takes precedence over automatic session recognition.

On Responses requests, Rayline recognises Codex by its `originator` header and reads its `prompt_cache_key` as the root conversation ID. Spawned subagents can share that root key; their `thread-id` identifies the parallel branch, rather than a separate conversation.

Where automatic harness session recognition is enabled, Rayline also reads native session headers, the session ID in Messages `metadata.user_id`, and Responses `prompt_cache_key` from other clients. When no identifier reaches it, Rayline can derive a conversation from the opening messages. Separate sessions with identical openings can then be grouped together. See [agent harness conversation grouping](/tools/more-tools#the-conversation-id).

Deployments without that automatic recognition treat requests without a supported conversation identifier as stateless. For explicit conversation boundaries across deployments, send `x-conversation-id`; do not reuse a `prompt_cache_key` across unrelated conversations and expect it to distinguish them.

See [API compatibility](/arc/reference/compatibility) and [errors and limits](/arc/reference/errors).
