```
POST https://api.rayline.ai/v1/routes
```

Model Routing picks the model and reasoning configuration for a request without running it. Execute the choice in your own stack.

## Authentication

Send your Rayline API key (`rlk-...`) in either header:

| Header | Value |
| --- | --- |
| `Authorization` | `Bearer $RAYLINE_API_KEY` |
| `x-api-key` | `$RAYLINE_API_KEY` |

See [API keys](/platform/api-keys).

## Request

Send the same body you would send to generate the turn, in any of three formats: [Anthropic Messages](https://docs.anthropic.com/en/api/messages), OpenAI Chat Completions, or OpenAI Responses. The fields below use the Messages names; Chat Completions and Responses bodies use their own equivalents (`messages` or `input`).

| Field | Required | Notes |
| --- | --- | --- |
| `messages` | Yes | A non-empty array of messages. ARC reads the whole conversation you send. |
| `system` | No | Your system prompt. |
| `tools` | No | Read with your system prompt: ARC encodes each tool's name, description and schema, and those tokens count in `usage.encoded_input_tokens`. |
| `model` | Yes | An ARC model ID: `arc-swift-1.0`, `arc-sage-1.0`, or `arc-1.0` (`arc-1` is also accepted), or its Contributor or zero data retention ID (`arc-swift-contributor-1.0`, `arc-swift-zdr-1.0` and so on), which routes like the plain ID. An organization on zero data retention must use the zero data retention IDs; see [data and privacy](/platform/data-privacy#arc-model-ids-choose-the-data-mode). Prefixed IDs such as `rayline/arc-swift` and unknown `arc-*` IDs such as `arc-2.0` return `400` (`unknown_model`); a provider model returns `400` (`arc_model_required`). |
| `routing` | No | ARC's [routing controls](#routing-controls): your value, routing temperature, candidate models, and prices. |
| `max_tokens` | Anthropic Messages only | Required in an Anthropic Messages body, as it is when you generate; it does not affect the route. Chat Completions and Responses bodies do not need it. |
| `temperature`, `stream` | No | Ignored. A route is always returned as a single JSON response. |

ARC reads the format from the body. A body with `input` is read as OpenAI Responses. A `messages` body is read as Anthropic Messages when it carries an Anthropic-only field, such as a top-level `system`, a `tool_use` or `tool_result` block, or a tool with `input_schema`; it is read as OpenAI Chat Completions when it carries a Chat-only marker, such as a `system` or `tool` role in `messages` or a tool with `function`. A `messages` body with neither, for example a single user message with string content, is read as OpenAI Chat Completions (`openai.chat.v1`). ARC reads the format from the body only; to make it unambiguous, include one of these markers, for example a `system` role message for Chat Completions or a top-level `system` for Anthropic Messages.

### Routing controls

`routing` is an object. Every member is optional; a member Rayline does not recognise is refused with `400` (`routing_unknown_member`), never ignored. Send V as `v_value`: its former name, `value_usd`, is refused the same way.

| Member | Type | Meaning |
| --- | --- | --- |
| `v_value` | number, 0.1 to 30 | Your value (V): what one successful result is worth to you, in US dollars. Adds a [`custom`](#custom-and-routing-echo) result decided at this value. Out-of-range values are refused, never clamped. Required with `arc-1.0`, `arc-contributor-1.0` and `arc-zdr-1.0`: without it the request is refused with `value_required`. With a Swift or Sage ID, in any data mode, it is refused with `tier_value_immutable`, even at the tier's fixed V (0.1 or 4.5); use `arc-1.0`, `arc-contributor-1.0` or `arc-zdr-1.0` for your own value. |
| `temperature` | number, 0 or more | Routing temperature: a softmax temperature over ARC's normalized scores for each result. 0 always takes the top choice. Uncapped on the Routes API. Separate from the model's generation `temperature`. |
| `models` | array of strings | The models ARC may choose from: up to 256 model IDs or `*` wildcards. Without it, ARC chooses from every model it can select. See [candidate models](#candidate-models). |
| `excluded_models` | array of strings | Models ARC must not choose: up to 256 model IDs or `*` wildcards. Wins over `models`. |
| `prices` | object | Your inference prices: up to 256 exact model IDs, each with at least one of `input`, `cache_read`, `cache_write`, and `output` in USD per million tokens. A leg you leave out is priced by your profile or the catalog. They change which model ARC selects, never what the route costs. See [bring your own prices](/arc/routes/prices). |
| `price_profile` | object | A saved [price profile](/arc/routes/prices#price-profiles): `{"id": "...", "version": 3}`. `version` is optional and defaults to the profile's current version. Can be combined with `prices`. |

```json
{
  "model": "arc-1.0",
  "messages": [{"role": "user", "content": "Review a database migration for data-loss risks."}],
  "routing": {
    "v_value": 2,
    "temperature": 0.5,
    "models": ["anthropic/*", "deepseek/deepseek-v4-pro-0813"],
    "excluded_models": ["anthropic/claude-opus*"],
    "prices": {
      "deepseek/deepseek-v4-pro-0813": {"input": 0.4, "output": 0.9}
    }
  }
}
```

Routes API requests are never used to train ARC.

### Candidate models

`models` and `excluded_models` decide which models ARC chooses from. Each entry is an exact model ID, such as `deepseek/deepseek-v4-pro-0813`, or a pattern where `*` matches any run of characters, such as `anthropic/*`. Matching is case-sensitive; `*` is the only wildcard. Entries are matched against the models the answering ARC release can select.

- Without `models`, every model ARC can select is a candidate. With it, only the matched models are: ARC never falls back to the full set.
- `excluded_models` removes models from the candidates, and wins over `models`.
- An entry that matches no model is refused with `unknown_model`, so a typo fails instead of being ignored. If no model is left after exclusions, the request is refused with `no_candidate_models`.
- A wildcard also matches models added to ARC later. The [`routing.models` echo](#custom-and-routing-echo) lists the models a route actually chose from.

Prices never change the candidates: a model you price but leave out of `models` is not a candidate, and a candidate you do not price keeps its profile or catalog price. For each model and price leg, ARC uses the first source that sets it: your inline `prices`, then the profile's model override, then the profile's provider discount applied to the catalog price, then the catalog price. See [bring your own prices](/arc/routes/prices).

### Conversation headers

| Header | Purpose |
| --- | --- |
| `x-conversation-id` | A stable ID for the conversation. Send the same value on every turn so each route accounts for the conversation so far. See [Conversations](#conversations). |

See [Conversation identity](#conversation-identity) for how the conversation ID is resolved.

## Response

```json
{
  "route_id": "rt_5f0c9a2e8b1d4c7fa6e3b2d19c8a7f60",
  "object": "route",
  "model": "deepseek/deepseek-v4-pro",
  "worker": "deepseek/deepseek-v4-pro@thinking-off",
  "provider": "openrouter",
  "thinking": { "mode": "off", "budget_tokens": null },
  "checkpoint": "arc-c82-dev.c82a1f3e",
  "alternatives": [
    {
      "model": "xiaomi/mimo-v2.5-pro",
      "worker": "xiaomi/mimo-v2.5-pro@thinking-on",
      "provider": "openrouter",
      "score": 0.62
    }
  ],
  "selected_pricing": {
    "input": 0.435,
    "cache_read": 0.003625,
    "cache_write": 0.435,
    "output": 0.87,
    "pricing_source": "catalog"
  },
  "warnings": ["episode_not_tracked: this cell keeps no episodes for route lookups, so the conversation did not influence this route"],
  "usage": { "encoded_input_tokens": 3040, "cache_read_tokens": 0 },
  "latency_ms": 212,
  "presets": {
    "swift": {
      "model": "deepseek/deepseek-v4-pro",
      "worker": "deepseek/deepseek-v4-pro@thinking-off",
      "provider": "openrouter",
      "thinking": { "mode": "off", "budget_tokens": null },
      "v_value": 0.1,
      "cost_weight": 10,
      "prices": { "basis": "catalog", "price_sha256": null }
    },
    "sage": {
      "model": "xiaomi/mimo-v2.5-pro",
      "worker": "xiaomi/mimo-v2.5-pro@thinking-on",
      "provider": "openrouter",
      "thinking": { "mode": "on", "budget_tokens": 8192 },
      "v_value": 4.5,
      "cost_weight": 0.2222222222222222,
      "prices": { "basis": "catalog", "price_sha256": null }
    }
  }
}
```

| Field | Type | Description |
| --- | --- | --- |
| `route_id` | string | Identifies this route. Include it when you contact support. |
| `object` | string | Always `route`. |
| `model` | string | The model to run. |
| `worker` | string | The model and configuration ARC scored, for example `xiaomi/mimo-v2.5-pro@thinking-on`. Two workers can share one model with different reasoning settings. |
| `provider` | string | The provider the worker is configured for. Omitted when the worker names none. |
| `thinking` | object | The reasoning configuration the choice was scored under. `mode` is `on` or `off`. `budget_tokens` is the reasoning budget, or `null` when thinking is off. Apply it as given: the choice was scored for this configuration, not for the model alone. |
| `thinking_level` | string | Present when the route includes a per-turn steering level, for example `up`, `down`, or `none`. Apply it as a private steering instruction; see [Applying effort](/arc/routes/applying-effort). |
| `checkpoint` | string | The ARC checkpoint that chose the route. |
| `alternatives` | array | Other workers ARC scored and did not choose, highest score first, each with `model`, `worker`, `provider`, and `score`. `score` is the number ARC ranked the worker by for this route: higher is better. It has no fixed range. Compare scores only within one response: each checkpoint scores on its own scale. Workers excluded by a hard constraint are not listed. This is not a fallback order. |
| `baseline` | object | A reference `model` and its rate card (`input`, `cache_read`, `cache_write`, `output`), for comparing cost. Omitted when the checkpoint declares no reference. |
| `selected_pricing` | object | The chosen worker's rate card: `input`, `cache_read`, `cache_write`, and `output`, in USD per million tokens, the same legs as [`routing.prices`](#routing-controls). `pricing_source` is where those prices came from, with the same values as a result's `prices.basis`: `catalog`, `caller`, `profile`, or `mixed`. |
| `warnings` | array of strings | Always present. Until the Routes API keeps conversations, every lookup carries `episode_not_tracked`. See [Warnings](#warnings). |
| `episode` | object | Reserved for conversation tracking, which the Routes API does not yet do; absent today (see [conversations](#conversations)). When present, `turn_index` counts the conversation's turns and `stayed` is `true` when ARC kept the previous turn's worker. |
| `usage` | object | `encoded_input_tokens` and `cache_read_tokens`: the tokens ARC read to choose this route, once for all results. These are the metered quantities; see [ARC pricing](/arc/pricing). `cache_read_tokens` is 0 until the Routes API reuses cached prefixes. |
| `latency_ms` | integer | Time ARC spent choosing the route. |
| `presets` | object | The routes at ARC Swift and ARC Sage. See [Presets](#presets). |
| `custom` | object | Present when you sent `routing.v_value`. See [Custom and routing echo](#custom-and-routing-echo). |
| `routing` | object | Present when you sent `routing`. |

ARC does not explain its choice, and `alternatives[].score` is a ranking, not a confidence measure.

### Presets

Every response carries `presets`, with the route at both fixed tiers, from the same single read of your request:

| Field | Meaning |
| --- | --- |
| `presets.swift` | The route at ARC Swift's value (V 0.1). |
| `presets.sage` | The route at ARC Sage's value (V 4.5). |

Each result has `model`, `worker`, `provider`, `thinking`, `thinking_level`, `v_value`, `cost_weight` (1 / `v_value`), `prices`, and, when you sent `routing.temperature`, `temperature`.

- `prices.basis` is where the result's model prices came from: `catalog` (Rayline catalog prices only), `caller` (your `routing.prices` set at least one leg), `profile` (your `routing.price_profile` set at least one leg), or `mixed` (both did). `prices.price_sha256` identifies the resolved prices of every candidate; it is `null` when you sent none of `models`, `excluded_models`, `prices`, or `price_profile`. See [check what was applied](/arc/routes/prices#check-what-was-applied).
- `temperature` reports `requested`, `applied`, and `status`: `greedy` (you asked for 0), `applied` (ARC drew the model at the `applied` temperature; `propensity` is the probability of the chosen model, and `pi` lists each candidate's probability), `not_applied` (with a `reason`), or `unsupported` (the serving path did not confirm it, so the result is the top choice).

The top-level `model`, `worker`, and `thinking` are the route for the `model` you requested. Presets are alternatives: running one does not change the conversation's state.

### Custom and routing echo

| Field | Present when | Meaning |
| --- | --- | --- |
| `custom` | You sent `routing.v_value` | The route at your value, with the same fields as a preset. |
| `routing` | You sent `routing` | Each member you sent, with `status` `applied` or `unsupported`. `unapplied_keys` lists every member that was not applied. |

Some members report more than their status:

| Echo | Fields |
| --- | --- |
| `routing.models` | `models`, the entries you sent, and `resolved`, the final list of candidate models after `excluded_models`. |
| `routing.excluded_models` | `excluded_models`, the entries you sent. |
| `routing.prices` | `models`, the resolved price of every candidate, with a `source` for each leg (`caller`, `profile`, or `catalog`); `unused`, the models you priced that are not candidates; and `price_sha256`, a hash of the resolved prices. Reported when you sent `prices` or `price_profile`. |
| `routing.price_profile` | The profile and the prices it resolved to; see [check the profile that was applied](/arc/routes/prices#check-the-profile-that-was-applied). |

Treat `unsupported` as not applied: ARC chose the route without that control, and the result says so rather than showing your value as used.

### Usage

`usage.encoded_input_tokens` and `usage.cache_read_tokens` count one read of your request, however many results the response carries. That read is what a route is billed for; see [ARC pricing](/arc/pricing).

## Conversations

The Routes API does not yet keep conversations: each lookup is routed on its own, as if it were the conversation's first turn, and ARC reads the whole request every time. Every lookup returns the `episode_not_tracked` warning, whether or not it sends a conversation ID; the response has no `episode`, and `usage.cache_read_tokens` is 0.

When conversation tracking ships, sending the same `x-conversation-id` on every turn will let ARC route each turn in light of the turns before it, including whether to stay on the current model, and re-use the context it already encoded, reported as `cache_read_tokens`. Sending the header today is harmless.

Keep one ID per conversation. For parallel subagents, give each subagent its own ID. Send one request per conversation at a time: a second concurrent request for the same conversation returns `429` until the first completes.

A conversation's state expires after a period of inactivity.

### Conversation identity

ARC takes the conversation ID from the first of these that is present:

1. The `x-conversation-id` header.
2. The `x-claude-code-session-id` header, which Claude Code sends on its own.

With neither, the request is stateless.

The body field `metadata.user_id` is not read. Anthropic defines it as a per-user identifier, and one ID for every conversation of a user would route those conversations in each other's context. Send `x-conversation-id` to identify the conversation.

The same order applies to a routed turn. Once the Routes API keeps conversations, a lookup and the turn it precedes will land on the same episode.

## Warnings

Each warning is a string of the form `code: explanation`. Treat the code as stable and the explanation as display text.

| Code | Meaning |
| --- | --- |
| `format_inferred` | The body had no field unique to one format, so ARC read it as Chat Completions. Add a format marker to the body (see [Request](#request)) to make it explicit. |
| `tools_not_encoded` | The request's tools did not influence this route. Current cells can return this warning even though the tools were encoded and billed; a fix is in progress. |
| `tool_schemas_not_encoded` | Tool names influenced this route; their descriptions and schemas did not. |
| `episode_not_tracked` | The Routes API does not yet keep conversations, so this lookup was routed on its own. Returned on every lookup today, with or without a conversation ID. |
| `checkpoint_not_pinned` | A requested checkpoint was ignored; the served checkpoint chose the route. |

## Errors and limits

Errors use the Anthropic error format: `{"type": "error", "error": {"type": "...", "message": "..."}}`.

Errors from the routing contract carry a stable `error.code`. A body ARC cannot read in its format returns `400` with only a message, for example `request body could not be read as anthropic.messages.v1 messages`.

| Status | `error.code` | Meaning | Retry? |
| --- | --- | --- | --- |
| `400` | | The body is not a JSON object with messages, or cannot be read in its format (for example, an Anthropic Messages body without `max_tokens`) | No; fix the request |
| `400` | `routing_invalid`, `routing_unknown_member` | `routing` is not an object, or has a member Rayline does not support | No |
| `400` | `value_invalid`, `value_out_of_bounds` | `routing.v_value` is not a number in 0.1–30 | No |
| `400` | `value_required` | `model` is `arc-1.0`, `arc-contributor-1.0` or `arc-zdr-1.0` without `routing.v_value` | No; add `routing.v_value` |
| `400` | `tier_value_immutable` | `routing.v_value` was sent with a Swift or Sage ID, which decides at its fixed V | No; drop `routing.v_value`, or use `arc-1.0` |
| `400` | `value_not_accepted` | `routing.v_value` was sent with a model that is not an ARC ID | No; use `arc-1.0` with `routing.v_value` |
| `400` | `arc_model_required` | `model` is not an ARC ID, such as a provider model | No; set `model` to `arc-swift-1.0`, `arc-sage-1.0`, or `arc-1.0` with `routing.v_value`, or its Contributor or zero data retention ID |
| `400` | `temperature_invalid` | `routing.temperature` is not a finite number of 0 or more | No |
| `400` | `models_invalid` | `routing.models` or `routing.excluded_models` is not an array of strings, or has more than 256 entries | No |
| `400` | `unknown_model` | `model` is a prefixed ID or an unknown `arc-*` ID such as `arc-2.0`, or an entry in `routing.models` or `routing.excluded_models` matches no model ARC can select | No; fix the ID or the entry |
| `400` | `no_candidate_models` | No model is left after `routing.models` and `routing.excluded_models` | No |
| `400` | `prices_invalid`, `price_leg_invalid`, `unknown_price_model` | `routing.prices` is malformed, has a negative or non-finite price, or names a model ARC cannot select | No |
| `400` | `price_profile_invalid` | `routing.price_profile` is not `{id, version?}` with a valid ID and a positive integer version. Other profile errors are listed under [price profiles](/arc/routes/prices#price-profiles) | No |
| `401` | | Missing or invalid API key | No |
| `402` | | `error.type` is `billing_error`: the workspace has no balance to pay for the route. The message links to the top-up page | No; [add funds](/platform/billing#which-balance-pays) |
| `403` | `zdr_model_required` | The organization uses zero data retention and `model` is not a zero data retention ID. The message names the ID to use | No; use that ID |
| `403` | `contributor_models_off` | `model` is a Contributor ID and **Allow Contributor models** is off for the organization | No; use another ID, or an owner turns Contributor models on |
| `404` | `model_not_found`, `model_not_served` | The ARC model is not serving in this environment | No |
| `413` | | The request body is too large | No |
| `429` | `rate_limited` | Rate limit reached, or the conversation already has a request in progress | Yes, after `Retry-After` seconds |
| `502` | `inconsistent_upstream` | The routing service returned an inconsistent answer | Yes, with backoff |
| `503` | `unavailable` | The Routes API is temporarily unavailable | Yes, with backoff |
| `504` | `timeout` | The route did not complete in time | Yes, with backoff |
| `529` | `capacity` | ARC is at capacity | Yes, with backoff |

Each account can make 30 Routes API requests per minute across all of its keys. A route normally completes within about 1.5 seconds.

See [Model Routing](/arc/routes) for the integration loop and [errors and limits](/arc/reference/errors) for troubleshooting.
