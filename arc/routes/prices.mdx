ARC weighs each candidate model's expected quality against its expected cost. By default the cost comes from the Rayline catalog. If you pay different prices, for example through negotiated provider rates, a different provider, or your own hardware, send them with the request so ARC chooses for your costs.

Prices apply to the [Routes API](/arc/routes) only. They change which model ARC selects. They do not change the Routes API charge, Swift or Sage rates, Rules Router billing, or what your provider bills you.

## Send prices

Add `routing.prices` to the Routes API request: a map from model ID to your prices in US dollars per million tokens.

```json
{
  "model": "arc-sage-1.0",
  "messages": [{"role": "user", "content": "Refactor the billing module."}],
  "routing": {
    "models": ["deepseek/deepseek-v4-pro-0813", "qwen/qwen3.8-27b"],
    "prices": {
      "deepseek/deepseek-v4-pro-0813": {"input": 0.3, "output": 0.7},
      "qwen/qwen3.8-27b": {"input": 0, "cache_read": 0, "cache_write": 0, "output": 0}
    }
  }
}
```

- **Each leg is optional:** `input`, `cache_read`, `cache_write`, `output`, but each model you price needs at least one; an empty entry is refused with `prices_invalid`. A leg you leave out keeps your [price profile's](#price-profiles) price, or the catalog price. 0 is a valid price, for example for a model on your own hardware; a negative or non-finite price is refused with `price_leg_invalid`.
- **Up to 256 models, by exact ID.** Use the model IDs a route returns in `model` and `alternatives[].model`, such as `deepseek/deepseek-v4-pro-0813`. Wildcards are not accepted here; use a profile's provider discount to price every model from a provider. A model ID that ARC cannot select is refused with `unknown_price_model`.
- **Prices do not choose the candidates.** Models you do not price keep their profile or catalog prices. To limit ARC to certain models, list them in `routing.models`, or remove some with `routing.excluded_models`; see [candidate models](/arc/reference/routes#candidate-models). A model you price that is not a candidate is allowed and reported as `unused`.

ARC never substitutes a catalog price for a malformed entry: an invalid request is refused with a `400` naming the problem.

## Check what was applied

The response's `routing.prices` reports:

- **`status`**: `applied` or `unsupported`.
- **`models`**: the resolved price of every candidate model, with a `source` for each leg: `caller` (your `routing.prices`), `profile` (your price profile), or `catalog`.
- **`unused`**: models you priced that were not candidates.
- **`price_sha256`**: the SHA-256 of the resolved prices of every candidate, as RFC 8785 canonical JSON: `{"schema": "arc-route-prices.v1", "prices": {"<model ID>": {"input": ..., "cache_read": ..., "cache_write": ..., "output": ...}}}`. Each result's `prices.price_sha256` carries the same value. Keep it with your own records to show which prices a route used.

```json
{
  "routing": {
    "prices": {
      "status": "applied",
      "models": {
        "deepseek/deepseek-v4-pro-0813": {
          "input": 0.3, "cache_read": 0.003625, "cache_write": 0.435, "output": 0.7,
          "source": {"input": "caller", "cache_read": "catalog", "cache_write": "catalog", "output": "caller"}
        },
        "qwen/qwen3.8-27b": {
          "input": 0, "cache_read": 0, "cache_write": 0, "output": 0,
          "source": {"input": "caller", "cache_read": "caller", "cache_write": "caller", "output": "caller"}
        }
      },
      "unused": [],
      "price_sha256": "<64 hexadecimal characters>"
    }
  }
}
```

Each result's `prices.basis` summarizes where its model's prices came from: `catalog` when neither your inline prices nor a profile set any leg, `caller` or `profile` when only that source did, and `mixed` when both did.

If `status` is `unsupported`, the route was chosen at catalog prices.

## Price profiles

A price profile saves your prices on the Rayline Platform so you can reference them by ID instead of sending a table with every request. Owners and billing members create and edit profiles under **Price profiles**; any active member of the organization can use them. Test a profile in the **Playground** before you use it from code.

A profile holds rules rather than a fixed table:

- **Provider discounts:** a `discount_percent` from 0 to 100 for a provider, applied to all four legs of every eligible model from that provider.
- **Model overrides:** a price for any of `input`, `cache_read`, `cache_write`, or `output` on one model. An override wins over the provider discount; a leg you do not override follows the discount, or the catalog rate when the provider has none.

ARC resolves the rules at routing time against the current catalog rates, so a provider discount also covers models from that provider added later. Rules apply only to eligible models, the models an ARC checkpoint routes to.

### Use a profile

<Note>
Saved price profiles are not yet enabled on the production API: a request that names one returns `503` `price_profile_unavailable`. Until they are, send your prices inline with [`routing.prices`](#send-prices).
</Note>

Reference the profile with `routing.price_profile`, using the ID shown in the profile's version details. Add `version` to pin a version for reproducible runs; without it, the profile's current version is used.

```json
{
  "model": "arc-1.0",
  "messages": [{"role": "user", "content": "Refactor the billing module."}],
  "routing": {
    "price_profile": {"id": "YOUR_PROFILE_ID", "version": 3}
  }
}
```

You can send `routing.prices` with a profile. For each model and leg, ARC uses the first source that sets it:

1. Your inline `routing.prices`.
2. The profile's model override.
3. The profile's provider discount, applied to the catalog price.
4. The catalog price.

A profile does not choose the candidates either: a profile usually prices far more models than one request needs. Limit the candidates with `routing.models` and `routing.excluded_models`.

### Check the profile that was applied

The response's `routing.price_profile` reports the profile and the prices it resolved to. Suppose version 3 of the profile above gives Anthropic models 20% off and overrides the input and output prices of `openai/gpt-6-luna` (abridged):

```json
{
  "routing": {
    "price_profile": {
      "status": "applied",
      "id": "YOUR_PROFILE_ID",
      "version": 3,
      "content_hash": "sha256:<64 hexadecimal characters>",
      "schema": "price-profile-rules.v1",
      "prices": {
        "anthropic/claude-sonnet-5.5": {"input": 1.6, "cache_read": 0.08, "cache_write": 2, "output": 8},
        "openai/gpt-6-luna": {"input": 0.08, "cache_read": 0.01, "cache_write": 0.125, "output": 0.4}
      },
      "unpriced": [],
      "ineligible": [],
      "not_offered": [],
      "card_version": 42
    }
  }
}
```

- **`status`** is `applied` or `unsupported`, as for inline prices.
- **`prices`** is the table the profile resolved to. The `routing.prices` echo reports the final price of each candidate, with `profile` as the `source` of each leg the profile set, and its `price_sha256`.
- **`unpriced`** lists covered models with no catalog rate for a leg you did not override; **`ineligible`** lists overrides of models ARC no longer routes to. Both are left out of `prices`.
- **`not_offered`** lists priced models that the ARC release answering the request does not offer; a tier or pinned release can offer fewer models than the profile prices. They are dropped from `prices` and the route goes ahead without them. A profile saved before rules existed is handled like inline `routing.prices`: a model the release does not offer fails the request with `unknown_price_model`, and its `not_offered` is always empty.
- **`content_hash`** identifies the saved rules, and **`card_version`** the catalog rates they were resolved against. A profile saved before rules existed reports `schema: "legacy"` and `card_version: null`. `content_hash` and `price_sha256` hash different things; do not compare them.

ARC never substitutes catalog prices for a profile it cannot resolve:

| Status | `error.code` | Meaning |
| --- | --- | --- |
| `400` | `price_profile_invalid` | `routing.price_profile` is not an object with a valid `id` and, optionally, a positive integer `version` |
| `403` | `price_profile_forbidden` | You are not an active member of the key's organization |
| `404` | `price_profile_not_found` | No such profile or version in your organization |
| `409` | `price_profile_archived` | The profile is archived; restore it on the Platform first |
| `409` | `price_profile_unpriced` | The profile resolves to no priced model, or the answering ARC release offers none of the models it prices. A leg your inline `routing.prices` sets is never reported as unpriced |
| `503` | `price_profile_unavailable` | Profiles are not enabled in this environment, or profile storage or catalog rates are temporarily unavailable |

### Routes API only

Prices, price profiles, and candidate models are accepted only on the Routes API (`/v1/routes`). Generation endpoints such as `/v1/chat/completions` and `/v1/messages` refuse `routing.models`, `routing.excluded_models`, `routing.prices`, and `routing.price_profile` with `400` `routes_only_member`. Profiles never change how ARC Swift, ARC Sage, or `arc-1.0` serve or bill generation requests.
