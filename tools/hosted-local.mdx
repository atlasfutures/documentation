A request has three independent locations: **where the gateway runs**, **where ARC chooses a model**, and **where that model generates the answer**. “Local” needs to name which of these it means.

| Component | What it does | What running it locally means |
| --- | --- | --- |
| Rayline Local gateway | Receives your tool's request and forwards it to a configured endpoint | The gateway runs on your computer. Inference can still be entirely in the cloud. |
| Inference model | Generates the answer and tool calls | A model server, such as llama.cpp, runs on your hardware. |
| ARC routing model | Chooses where to send an inference request | ARC makes the routing decision on your hardware. Its chosen inference endpoints can be cloud, on-device, or a mixture. |

## Connect through the cloud or Rayline Local

| Connection | Request path | Where ARC runs in these guides | Where inference runs |
| --- | --- | --- | --- |
| Rayline platform (default) | Your tool → hosted Rayline | Hosted Rayline | Cloud |
| Rayline Local gateway | Your tool → local gateway → hosted Rayline | Hosted Rayline | Cloud |

The integration guides cover these two cloud-backed paths. **You do not need a local inference model to use a local gateway.** Both charge inference to your Rayline workspace.

A tool can connect directly when it supports the required API protocol, a custom base URL, and Rayline authentication. A launcher may choose a local gateway for configuration or protocol handling even when a manual direct connection is possible. Check the individual guide; a `rayline <tool>` command does not by itself tell you which path it uses.

## Configure a cloud-forwarding gateway

Install [Rayline](/rules-router/cli#install). Save this configuration as `router.json`:

```json
{
  "endpoints": [{
    "id": "rayline",
    "protocol": "anthropic_messages",
    "base_url": "https://api.rayline.ai",
    "api_key_env": "RAYLINE_KEY",
    "models": ["arc-sage", "arc-swift", "arc-1.0", "rayline-router"]
  }],
  "routes": {
    "main": { "endpoint": "rayline", "model": "arc-sage" },
    "subagent": { "endpoint": "rayline", "model": "arc-sage" }
  }
}
```

Load your [Rayline API key](/platform/api-keys) into `RAYLINE_KEY`, then start the gateway. The ports below are explicit choices; change them if another process already uses them.

```bash
RAYLINE_METRICS_PORT=23812 rld serve \
  --no-local-model \
  --local-router-port 23811 \
  --adapter-port 23808 \
  --injector-port 23809 \
  --router-config-path "$PWD/router.json" \
  --data-dir "$PWD/rayline-gateway-data"
```

Leave this process running. In a **different shell**, configure the client with base URL `http://127.0.0.1:23811` (OpenCode adds `/v1`) and placeholder client key `local-client`. This gateway holds the real upstream key and forwards cloud requests; it does not download a local model.

Check requests in [Rayline Usage](/platform/usage) to see the selected ARC tier, served model, and charge. Stop this gateway with Ctrl+C when finished.

## On-device inference

A local inference endpoint needs its own model installation, hardware capacity, and routing configuration. A mixed route can send some calls to cloud models and others to your on-device model. See [local models](/rules-router/guides/local-models).


## Run ARC locally

Running the ARC routing model locally is a third deployment choice. It does not require that every selected inference model also run locally. Rayline Local does not currently include ARC weights; see [open weights and self-hosting](/arc/open-source) for source and artifact availability.

## Subscription billing

Subscription paths, such as `rayline codex --subscription`, send the main agent to your existing subscription. That subscription bills those requests rather than Rayline. Consult the tool guide before mixing subscription and Rayline API paths.
